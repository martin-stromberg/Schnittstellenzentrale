# Release Notes

## Important Notes Before Update

- The application now targets .NET 11: install the .NET 11.0 Runtime (ASP.NET Core) on the host before updating; the .NET 10 runtime is no longer sufficient.

## What's New

- Platform upgrade to .NET 11: all projects now target `net11.0` under SDK 11.0.100, CI builds pin `dotnet-version 11.0.x`, and the floating framework package baseline moved from `10.0.*` to `11.0.*` (resolved 11.0.0); `Microsoft.AspNetCore.OData 10.0.0-preview.2` remains pinned and is verified running under .NET 11.
- Dependency cleanup in `Schnittstellenzentrale.Infrastructure`: the project now consumes ASP.NET Core APIs via `FrameworkReference Microsoft.AspNetCore.App` instead of the legacy packages `Microsoft.AspNetCore.Http.Abstractions` 2.3.0 and `Microsoft.AspNetCore.SignalR.Core` 1.2.10; redundant `Microsoft.Extensions.*`/`Microsoft.JSInterop`/`System.Security.Cryptography.Pkcs` package references covered by the shared framework were removed as well, and `Microsoft.AspNetCore.SignalR.Client` moved to the web project where it is actually used.
- Public GitHub Page presentation site at https://martin-stromberg.github.io/Schnittstellenzentrale/: static German page introducing the application with feature cards, real Playwright-generated screenshots (light and dark), a `releases/latest` download reference and links to the repository, `docs/help/` and `LEGAL.md`; sources live in `site/` and deploy automatically via the `pages.yml` workflow.
- Centralized SignalR notification policy (`INotificationPolicy`): every mutating operation — REST, all mutating OData operations on the four entity sets, endpoint header/query-parameter routes, import apply and the startup synchronization — now raises exactly one change notification in team storage mode and none in user mode; the duplicate notification when saving an endpoint from the UI has been removed.
- Unified endpoint aggregate update: replacing an endpoint — scalar values plus the full `Headers` and `QueryParameters` sets — now runs as a single server-side operation shared by the REST update endpoint, the OData `PUT`/`PATCH` operations on `Endpoints` and the import apply paths; optimistic concurrency via `RowVersion` is unchanged.
- Atomic deletion of application groups: `DELETE /api/application-groups/{id}` accepts an optional `content` parameter — `delete` removes the group together with all contained applications, endpoints and endpoint groups in one transactional operation; `detach` (default) ungroups the applications and removes only the group. Any failure rolls back the entire operation.
- New REST endpoint `POST /api/applications/{id}/swagger-import/apply` applies a previously computed Swagger import diff to an application with full validation (token, existence, interface type, aggregate integrity, concurrency via `RowVersion`).
- Unified Swagger import execution path: imports and the startup synchronization of system applications now run through the same apply endpoint.
- Unified API execution path in the workspace area: all endpoint and endpoint-group operations (create, rename, delete, count queries) as well as deleting application groups with content now go through the REST API with consistent context headers and a single change-notification policy — removing duplicated notification logic and multi-step UI delete flows.
- Hardened CI test suite against flaky environment-sensitive tests: the suite is now split into two lanes — a blocking regular lane (`Category!=OsInterface`) that feeds the 70% coverage gate, and a best-effort OS-interface lane (`Category=OsInterface`, separate CI job with `continue-on-error`) for environment-sensitive tests such as Playwright and temp-filesystem tests, which carry `[OsInterface]`/`[Trait("Category","OsInterface")]`; the `Flaky` trait (only allowed together with `OsInterface`) enables exactly one automatic retry within the OS lane; a TRX-based flake statistic creates quarantine issues on threshold violations; the convention is documented in `docs/help/stabilitaet/os-interface-tests.md` — to retry, run `gh run rerun --job <id>` for the OS job only.

## Wichtige Hinweise vor dem Update

- Die Anwendung läuft jetzt unter .NET 11: Vor dem Update ist die .NET 11.0 Runtime (ASP.NET Core) auf dem Host zu installieren; die .NET-10-Runtime reicht nicht mehr aus.

## Neuerungen

- Plattform-Upgrade auf .NET 11: Alle Projekte zielen auf `net11.0` unter SDK 11.0.100, die CI-Builds pinnen `dotnet-version 11.0.x`, und die Floating-Baseline der Framework-Pakete wurde von `10.0.*` auf `11.0.*` gehoben (aufgelöst: 11.0.0); `Microsoft.AspNetCore.OData 10.0.0-preview.2` bleibt gepinnt und ist unter .NET 11 verifiziert.
- Abhängigkeits-Bereinigung in `Schnittstellenzentrale.Infrastructure`: ASP.NET-Core-APIs kommen jetzt über `FrameworkReference Microsoft.AspNetCore.App` statt aus den Legacy-Paketen `Microsoft.AspNetCore.Http.Abstractions` 2.3.0 und `Microsoft.AspNetCore.SignalR.Core` 1.2.10; die ebenfalls vom Shared Framework abgedeckten `Microsoft.Extensions.*`-/`Microsoft.JSInterop`-/`System.Security.Cryptography.Pkcs`-Paketreferenzen wurden entfernt, und `Microsoft.AspNetCore.SignalR.Client` wurde ins Web-Projekt verschoben, wo es tatsächlich genutzt wird.
- Öffentliche GitHub-Page-Präsentationsseite unter https://martin-stromberg.github.io/Schnittstellenzentrale/: statische deutschsprachige Seite mit Vorstellung der Anwendung, Feature-Kacheln, echten Playwright-Screenshots (hell und dunkel), `releases/latest`-Download-Verweis sowie Links auf Repository, `docs/help/` und `LEGAL.md`; die Quellen liegen in `site/` und werden über den `pages.yml`-Workflow automatisch deployt.
- Zentrale SignalR-Benachrichtigungs-Policy (`INotificationPolicy`): Jede mutierende Änderung — REST, alle mutierenden OData-Operationen der vier Entity-Sets, Endpunkt-Header-/Query-Parameter-Routen, Import-Apply und Startabgleich — löst im Team-Speichermodus genau eine Änderungs-Benachrichtigung aus und im Benutzermodus keine; die doppelte Benachrichtigung beim UI-Speichern eines Endpunkts entfällt.
- Einheitliches Endpunkt-Aggregat-Update: Das Ersetzen eines Endpunkts — Skalarwerte plus die vollständigen Mengen `Headers` und `QueryParameters` — läuft als eine gemeinsame serverseitige Operation, die vom REST-Update-Endpunkt, den OData-`PUT`/`PATCH`-Operationen auf `Endpoints` und den Import-Apply-Pfaden genutzt wird; die Optimistic-Concurrency über `RowVersion` bleibt unverändert.
- Atomares Löschen von Anwendungsgruppen: `DELETE /api/application-groups/{id}` akzeptiert den optionalen Parameter `content` — `delete` entfernt die Gruppe samt aller enthaltenen Anwendungen, Endpunkte und Endpunktgruppen in einer transaktionalen Operation; `detach` (Standard) löst die Anwendungen aus der Gruppe und entfernt nur die Gruppe. Jeder Fehlschlag setzt die gesamte Operation zurück.
- Neuer REST-Endpunkt `POST /api/applications/{id}/swagger-import/apply` wendet einen zuvor berechneten Swagger-Import-Diff mit vollständiger Validierung auf eine Anwendung an (Token, Existenz, Interface-Typ, Aggregat-Integrität, Nebenläufigkeit über `RowVersion`).
- Einheitlicher Swagger-Import-Ausführungspfad: Importe und der Startabgleich von Systemanwendungen laufen über denselben Apply-Endpunkt.
- Einheitlicher API-Ausführungspfad im Workspace-Bereich: Sämtliche Endpunkt- und Endpunktgruppen-Operationen (Anlegen, Umbenennen, Löschen, Zählabfragen) sowie das Löschen von Anwendungsgruppen mit Inhalt laufen über die REST-API mit konsistenten Kontext-Headern und einer einzigen Benachrichtigungs-Politik — doppelte Benachrichtigungslogik und mehrstufige UI-Löschabläufe entfallen.
- Gehärtete CI-Test-Suite gegen flaky, umgebungssensitive Tests: Die Suite ist in zwei Lanes getrennt — eine blockierende reguläre Lane (`Category!=OsInterface`), die das 70-%-Coverage-Gate speist, und eine Best-Effort-OS-Schnittstellen-Lane (`Category=OsInterface`, eigener CI-Job mit `continue-on-error`) für umgebungssensitive Tests wie Playwright- und Temp-Dateisystem-Tests, die `[OsInterface]`/`[Trait("Category","OsInterface")]` tragen; das `Flaky`-Trait (nur in Kombination mit `OsInterface` zulässig) erlaubt genau einen automatischen Einmal-Retry in der OS-Lane; eine TRX-basierte Flake-Statistik erzeugt bei Schwellwertüberschreitung ein Quarantäne-Issue; die Konvention ist in `docs/help/stabilitaet/os-interface-tests.md` dokumentiert — für einen Retry gilt `gh run rerun --job <id>` ausschließlich für den OS-Job.
